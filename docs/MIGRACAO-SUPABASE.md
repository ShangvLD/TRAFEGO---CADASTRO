# Migração Turso → Supabase (PostgreSQL)

Guia da troca do banco: sai o **Turso** (SQLite na nuvem), entra o **Supabase**
(PostgreSQL). O deploy continua no **Vercel** — só o banco muda.

O **código já foi adaptado** (`src/db.js` agora fala PostgreSQL via driver `pg`).
O que falta é infraestrutura: criar o schema, importar os dados e trocar a
variável de ambiente no Vercel.

> **Regra de ouro:** o Turso só é desligado no final (Fase 6), depois de o
> Vercel estar rodando no Supabase e o Power Automate ter sido testado.

---

## O que mudou no código

| Antes (Turso/SQLite) | Agora (Supabase/PostgreSQL) |
| --- | --- |
| `@libsql/client` | `pg` (driver PostgreSQL, 100% JS) |
| `TURSO_DATABASE_URL` + `TURSO_AUTH_TOKEN` | `DATABASE_URL` (uma só variável) |
| Banco em arquivo local no dev (`data/trafego.db`) | Sempre no Supabase (não existe mais modo arquivo) |
| `id INTEGER AUTOINCREMENT` | `integer GENERATED BY DEFAULT AS IDENTITY` |
| `COLLATE NOCASE` no e-mail | índice único em `lower(email)` |
| `expira_em INTEGER` (sessões) | `expira_em bigint` |

A camada de consulta **não mudou de cara**: `db.prepare(sql).get/all/run()`
continua igual. O `src/db.js` traduz na hora as diferenças de dialeto:

- `?` → `$1, $2, $3…`
- `datetime('now','localtime')` → `to_char(now() AT TIME ZONE 'UTC', 'YYYY-MM-DD HH24:MI:SS')`
- `datetime(coluna)` → `coluna` (o texto `AAAA-MM-DD HH:MM:SS` já ordena certo)

Por isso `usuarios.js`, `solicitacoes.js` e `session-store.js` tiveram só
retoques (`RETURNING id` nos INSERTs e `lower()` nas buscas por e-mail).

### Sobre o fuso horário das datas

As datas continuam gravadas como **texto em UTC**, exatamente como o Turso
fazia — para as linhas novas ficarem coerentes com as 51 antigas. Se um dia
quiser passar a gravar no horário de Brasília, troque uma linha em
[src/db.js](../src/db.js): `const FUSO = 'UTC'` → `'America/Sao_Paulo'`.
Isso afeta só os registros criados depois da troca.

## Fase 0 — Pegar a connection string do Supabase

1. Abra o projeto em **https://supabase.com/dashboard**.
2. Se ainda não definiu a senha do banco: **Settings > Database >
   Database password > Reset database password**. Guarde a senha.
3. Clique em **Connect** (no topo da página) → aba **Connection string** →
   **Transaction pooler**.
4. Copie a URL. Ela tem esta cara (porta **6543**):

   ```
   postgresql://postgres.ctlymegxsnwsqpabkhwd:[YOUR-PASSWORD]@aws-0-us-west-1.pooler.supabase.com:6543/postgres
   ```

5. Troque `[YOUR-PASSWORD]` pela senha do passo 2.

> **Por que o pooler (6543) e não a conexão direta (5432)?** No Vercel cada
> requisição pode subir uma instância nova da função. Sem pooler, isso estoura
> o limite de conexões do Postgres rapidinho. O pooler em modo *transaction*
> resolve — e o driver `pg` funciona bem nele porque usamos consultas
> parametrizadas simples, sem prepared statements nomeados.

## Fase 1 — Apontar a máquina local para o Supabase

No `.env` do projeto (na sua máquina), **substitua** as linhas do Turso por:

```
DATABASE_URL=postgresql://postgres.ctlymegxsnwsqpabkhwd:SUA-SENHA@aws-0-us-west-1.pooler.supabase.com:6543/postgres
```

Mantenha `TURSO_DATABASE_URL` e `TURSO_AUTH_TOKEN` **comentados mas guardados**
até a Fase 6 — eles ainda servem se precisar reexportar os dados antigos.

## Fase 2 — Exportar os dados do Turso

Já feito (o dump está em `data/dump-turso.json`: 2 usuários e 51 solicitações),
mas o comando é este, se precisar rodar de novo:

```powershell
npm run exportar-turso
```

É **somente leitura** — não mexe em nada no Turso. O arquivo fica em
`data/`, que está no `.gitignore` (contém hashes de senha; nunca versionar).

## Fase 3 — Criar o schema e importar os dados no Supabase

Um comando só. Ele cria as tabelas/índices (se não existirem) e importa o dump
**preservando os ids e as datas originais**, tudo dentro de uma transação:

```powershell
npm run importar-supabase
```

Saída esperada:

```
Schema verificado/criado no Supabase.
  ✓ usuário     #1  ...
  ✓ 51 solicitação(ões) importada(s)
Sequências de id reposicionadas.
Pronto. No Supabase agora: 2 usuário(s), 51 solicitação(ões).
```

Se as tabelas já tiverem conteúdo, o script **cancela** para não duplicar nada.
Para apagar e importar do zero:

```powershell
npm run importar-supabase -- --limpar
```

> As **sessões** não são migradas. Todo mundo faz login de novo — é esperado.

Confira no painel: **Table Editor** → tabelas `usuarios`, `solicitacoes`, `sessoes`.

## Fase 4 — Testar local

```powershell
npm start
```

Abra http://localhost:3000 e verifique:

- [ ] login funciona (usuário e senha antigos, que vieram no dump)
- [ ] o painel do responsável lista as 51 solicitações, com as datas certas
- [ ] aprovar/reprovar um cliente grava e continua gravado depois do F5
- [ ] a área do solicitante mostra só as solicitações do e-mail logado
- [ ] `npm run consultar` mostra o resumo do banco

## Fase 5 — Trocar a variável no Vercel

1. **Vercel > o projeto > Settings > Environment Variables**.
2. **Adicione** `DATABASE_URL` com a mesma URL do pooler (marque os ambientes
   *Production*, *Preview* e *Development*).
3. **Remova** `TURSO_DATABASE_URL` e `TURSO_AUTH_TOKEN`.
4. Suba o código:

   ```powershell
   git add -A
   git commit -m "Migracao do banco: Turso -> Supabase (PostgreSQL)"
   git push
   ```

5. O Vercel faz o deploy automático. Se você mexeu nas variáveis **depois** do
   push, force um **Redeploy** (as variáveis só entram em um build novo).
6. Teste a URL de produção com a mesma lista da Fase 4.
7. Teste o webhook do Forms: `npm run testar-webhook` apontando para a URL de
   produção, ou mande uma resposta de verdade pelo Forms e confira se ela
   aparece no painel.

---

## Fase 6 — Desligar o Turso

Só depois de tudo acima confirmado, com o Vercel rodando no Supabase há alguns
dias e o Forms entregando respostas normalmente:

1. Guarde uma cópia do `data/dump-turso.json` fora do projeto (pen drive,
   OneDrive) — é o seu backup do estado antigo.
2. No painel do Turso, apague o banco `trafego-cadastro`.
3. Limpeza opcional no código:

   ```powershell
   npm uninstall @libsql/client
   ```

   E remova `src/exportar-turso.js`, os scripts `exportar-turso` /
   `importar-supabase` do `package.json` e as linhas do Turso no `.env.example`.

## Problemas comuns

**`DATABASE_URL não definida`**
O `.env` não tem a variável, ou você está rodando de outra pasta. No Vercel,
confira Settings > Environment Variables e faça um Redeploy.

**`password authentication failed for user "postgres"`**
Senha errada na URL, ou caracteres especiais não escapados. Se a senha tem
`@`, `:`, `/` ou `#`, troque-a por uma só com letras e números
(Settings > Database > Reset database password) — sai mais barato que escapar.

**`Connection terminated unexpectedly` / timeouts**
Confirme que está usando o host do **pooler** (`...pooler.supabase.com:6543`) e
não a conexão direta. Projeto free também **hiberna** depois de ~1 semana sem
uso: a primeira requisição acorda o banco e pode demorar alguns segundos.

**`relation "usuarios" does not exist`**
O schema não foi criado. Rode `npm run importar-supabase` (ele cria as tabelas
antes de importar) ou só `npm start`, que cria o schema no primeiro acesso.

**`duplicate key value violates unique constraint`**
Ao criar usuário: o e-mail já existe (a comparação ignora maiúsculas). Na
importação: as tabelas não estavam vazias — use `--limpar`.

**Banco pausado no Supabase**
No plano free, projetos sem uso por ~1 semana são pausados. Basta clicar em
**Restore** no painel; os dados continuam lá.
